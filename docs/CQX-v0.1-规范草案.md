# CQX v0.1 规范（草案）

**CQ eXtended：轻量富消息文本表示法**  
**版本：** 0.1-draft · **日期：** 2026-11-06 · **状态：** 设计草案

CQX 将文字与富消息元素写在同一个字符串中。它保留 CQ Code 的轻便写法，采用可嵌套的消息元素，并定义确定的解析、转义及序列化规则。

本文定义 CQX v0.1 的文本语法、内置元素、抽象消息树及规范化表示。CQX 可通过适配器映射到 OneBot、Satori 或平台 SDK。平台能力与网络接口由各自的适配器定义。

文中的 **必须** 表示实现符合本规范的必要条件，**应该** 表示推荐行为，**可以** 表示可选行为。

## 1. 基本格式

### 1.1 一条消息

CQX 文档是一段 Unicode 文本，普通文字与消息元素可以连续出现。以字节传输时应使用 UTF-8 编码；解析器不得改变正文的 Unicode 字符、空格及换行形式：

```cqx
你好，[@123456]！
看看这张图：[img cat.png]
[reply 98765]收到！[face 14]
```

上面的文字、提及、图片、回复引用和表情依次组成一条消息。换行属于正文的一部分。

### 1.2 两种元素写法

**简写**用于常见消息元素：

```cqx
[@123456]
[@all]
[img cat.png]
[reply 42]
[face 14]
```

**通用写法**用于严格序列化及任意扩展元素：

```cqx
[:at id="123456"/]
[:at type="all"/]
[:img src="cat.png"/]
[:reply id="42"/]
[:face id="14"/]
[:vendor.poll title="今天吃什么？"/]
```

每种简写都有唯一的通用形式。通用元素以 `[:` 开始；扩展元素必须使用通用写法。

### 1.3 原子元素与容器元素

| 形式 | 含义 | 示例 |
| --- | --- | --- |
| `[:name attr=value/]` | 原子元素；没有子节点 | `[:img src="cat.png"/]` |
| `[:name attr=value]...[/name]` | 容器元素；包含子节点 | `[:b]重要[/b]` |
| `[name ...]` | 已登记内置元素的简写 | `[img cat.png]` |
| `[name ...]...[/name]` | 已登记容器元素的简写 | `[forward]...[/forward]` |
| `[@identifier]` | 提及的专用简写 | `[@123456]` |

通用原子元素必须以 `/]` 结束。通用容器元素必须具有相同名称的结束标签 `[/name]`。空容器 `[:x][/x]` 与原子元素 `[:x/]` 是两种不同的数据结构。

### 1.4 元素名称

元素名称必须满足：

```regex
[A-Za-z][A-Za-z0-9_.-]*
```

属性名称必须满足：

```regex
[A-Za-z_][A-Za-z0-9_.-]*
```

名称区分大小写。内置元素名称均使用小写字母。扩展元素推荐使用带命名空间的名称，例如 `vendor.poll`、`acme.card`。

## 2. 属性

### 2.1 属性写法

属性由 `名称=值` 组成，多个属性之间以空白分隔：

```cqx
[:img src="cat.png" alt="一只猫"/]
[:vendor.card title="今日菜单" theme=dark/]
```

属性名称与等号、等号与属性值之间不能插入空格。同一元素中不得重复定义属性。属性顺序不影响消息语义。

### 2.2 属性值

属性值有两种形式：

- **裸值**：非空，且不含空格、制表符、回车、换行以及 `[`、`]`、`"`、`=`、`\`。例如 `cat.png`、`123`、`https://example.com/a.png`。
- **引号值**：双引号包围的 JSON 字符串，按 JSON 字符串规则解码。支持 `\"`、`\\`、`\n`、`\t`、`\uXXXX` 等转义。

```cqx
[img cat.png]
[img "cat photo.png"]
[img "https://example.com/p?q=[1,2]&v=3"]
[:file src="cid:abc123" name="我的\"文件\".pdf"/]
```

**所有属性值在 CQX 数据模型中都是字符串。** 因此 `id=00123` 保留为字符串 `"00123"`，`enabled=true` 保留为字符串 `"true"`。消息类型的 schema 可在验证阶段将特定字段解释为数值或布尔值。

当末尾裸值紧邻 `/]` 时，`/` 按自闭合结束标记解析，不属于裸值；这条规则同样适用于内置简写。需要保留末尾 `/` 时必须使用引号，例如：

```cqx
[:img src="https://example.com/a/"/]
```

### 2.3 位置参数

部分内置简写允许省略常用属性名称：

```cqx
[img cat.png]
[reply 42]
[file report.pdf name="报告.pdf"]
```

这三个简写分别使用位置参数 `src`、`id`、`src`。**CQX 没有注释语法**；`#` 是普通正文字符。

位置参数每个元素最多一个，由第 4 节内置元素表指定。位置参数与同名命名属性不得同时出现。通用形式 `[:name ...]` 只允许命名属性。

## 3. 纯文本与转义

### 3.1 正文字符

普通正文中的 `&`、`<`、`>`、`,`、`=`、`]` 均原样保留。

```cqx
这是一段普通文字：[note]、[1,2,3]、a&b、<hello>。
```

`[note]` 不属于已登记的简写，也没有使用 `[:` 通用前缀，因此按普通文本处理。

### 3.2 正文转义

CQX 正文只定义以下两种反斜杠转义：

| 写入 | 解析结果 |
| --- | --- |
| `\[` | 字面字符 `[` |
| `\\` | 字面字符 `\` |

其他反斜杠序列原样保留，例如 `\a`、`\d`。示例：

```cqx
真正的提及：[@123]
字面显示提及：\[@123]
Windows 路径：C:\Users\Alice
```

第一行包含 `at` 元素；第二行的 `[@123]` 是纯文本；第三行的单个反斜杠保持原样。

### 3.3 哪些方括号会被识别

解析器仅将以下形式作为标签起始候选：

1. `[:`：通用元素起始标记。
2. `[/name]`：合法名称的结束标签。
3. `[@identifier]`：提及专用简写。
4. `[name`：`name` 属于第 4 节登记的简写表，并紧跟空白、`]` 或 `/]`。

其他 `[` 作为普通文本。已识别的标记若语法错误，严格解析器必须报告错误。例如 `[img]` 缺少必需的 `src`；`[:x]` 缺少结束标签。未匹配的合法结束标签（如单独的 `[/x]`）也必须报错。需要逐字显示保留标记时，可写 `\[/x]`。

## 4. 内置消息元素

本节的元素名称与属性含义由 CQX v0.1 定义。所有内置原子元素均可使用通用自闭合写法；简写的原子元素允许省略自闭合斜杠。

### 4.1 原子消息元素

| 名称 | 常用简写 | 必需属性 | 可选属性 | 说明 |
| --- | --- | --- | --- | --- |
| `at` | `[@123]`、`[@all]` | `id` 或 `type="all"` | — | 提及用户或全体成员 |
| `img` | `[img cat.png]` | `src` | `alt` | 图片 |
| `reply` | `[reply 42]` | `id` | — | 回复某条消息 |
| `face` | `[face 14]` | `id` | — | 平台表情 |
| `audio` | `[audio voice.ogg]` | `src` | — | 音频 |
| `video` | `[video clip.mp4]` | `src` | — | 视频 |
| `file` | `[file report.pdf]` | `src` | `name` | 文件 |

`at` 的 `id` 与 `type="all"` 分别表示两种提及方式，必须选择一种，不得同时指定。`[@all]` 是保留简写；如用户 ID 确实为字符串 `all`，使用 `[:at id="all"/]`。

专用简写 `[@identifier]` 中的 `identifier` 必须满足 `[A-Za-z0-9_.-]+`。例如 `[@123]`、`[@user_1]` 合法。复杂标识符应使用 `[:at id="..."/]`。

媒体 `src` 表示资源标识符。可以使用 URL、相对引用或宿主约定的附件标识符（例如 `cid:abc`）。CQX 解析器不读取这些资源。

**示例：**

```cqx
[@123456]，请看：[img "https://example.com/cat.png" alt="猫"]
[reply 42]已处理。[face 14]
[audio voice.ogg][video demo.mp4]
[file report.pdf name="季度报告.pdf"]
```

### 4.2 容器消息元素

| 名称 | 简写形式 | 属性 | 含义 |
| --- | --- | --- | --- |
| `b` | `[b]内容[/b]` | — | 加粗 |
| `i` | `[i]内容[/i]` | — | 斜体 |
| `code` | `[code]内容[/code]` | — | 代码样式 |
| `link` | `[link href="..."]内容[/link]` | `href` 必需 | 超链接 |
| `forward` | `[forward]...[/forward]` | — | 合并转发容器 |
| `msg` | `[msg user=...]...[/msg]` | 见 4.3 节 | 合并转发中的消息节点 |

容器中可以混排文本与其他消息元素，除 `forward` 的特殊子节点规则外，正文空白全部保留。

```cqx
[b]注意：[/b]请查看[link href="https://example.com"]详细说明[/link]。
```

`code` 仍按照普通 CQX 规则解析其内部文本。需要展示字面标签时，必须转义 `[`，例如 `[code]\[img a.png][/code]`。

### 4.3 合并转发（`forward` 与 `msg`）

合并转发使用一个 `forward` 容器，内部依次放置 `msg` 节点。`msg` 有两种形式。

**引用已有消息：**

```cqx
[msg id=987654/]
```

这是原子元素，`id` 必需，且不得包含 `user` 属性或子内容。

**构造自定义消息：**

```cqx
[msg user=10001 name="Alice"]你好！[img cat.png][/msg]
```

这是容器元素，`user` 必需，`name` 可选，不得包含 `id` 属性。容器正文可以继续嵌套其他消息元素。

**完整合并转发：**

```cqx
[forward]
  [msg user=10001 name="Alice"]你好！[face 14][/msg]
  [msg user=10002 name="Bob"]看看这张图：[img cat.png][/msg]
  [msg id=987654/]
[/forward]
```

`forward` 的直接子节点必须是 `msg`；子节点之间允许用于排版的空白。解析器必须忽略这些间隔空白。出现非空白正文或其他类型的直接子元素时，必须报错。

自定义 `msg` 内部的换行和缩进**完全保留**。例如：

```cqx
[forward]
  [msg user=1]第一行
第二行[/msg]
[/forward]
```

`msg` 的正文恰好是 `第一行\n第二行`，包含一个真实换行。如果换行写在 `[msg user=1]` 后面，它也属于正文。

语法允许转发中的消息再次包含 `forward`。适配器根据平台能力决定是否能够发送嵌套转发。已有的合并转发记录可通过命名空间扩展表达，例如 `[:onebot.forward-ref id="f123"/]`；该扩展的业务语义由适配器定义。

### 4.4 扩展消息元素

所有合法名称都可以使用通用写法：

```cqx
[:acme.card title="选择操作"]
  [:acme.button label="同意" action="yes"/]
  [:acme.button label="拒绝" action="no"/]
[/acme.card]
```

解析器必须保留未知扩展元素的名称、属性、容器类型与子内容。内置元素中未列出的附加属性也应保留，其业务含义由适配器约定。扩展可以由插件定义属性约束和渲染规则，但不得改变 CQX 的基础词法、转义或空白规则。**扩展容器内的排版换行也会保留为文本节点**；只有 `forward` 使用第 5 节的特殊空白规则。

## 5. 空白与换行

CQX 按 Unicode 字符保留正文。解析器不得自动修剪首尾空白、合并多个空格、修改缩进或统一换行符。

CQX v0.1 唯一忽略容器内排版空白的内置元素是 `forward`：它的直接文本子节点若只包含空格 `U+0020`、制表符 `U+0009`、回车 `U+000D` 和换行 `U+000A`，解析后移除；其他字符按非排版文本处理并报错。

例：

```cqx
[msg user=1]
  第一行
  第二行
[/msg]
```

这段正文包含开头的换行、两行的两个缩进空格，以及结束标签前的换行。规范化序列化仍然保留这些正文字符。

## 6. 数据模型

解析结果是按顺序排列的节点数组（Document）。CQX 定义两类节点：

**Text 节点**

```json
{"type":"text","text":"你好 "}
```

**Element 节点**

```json
{
  "type": "element",
  "name": "at",
  "attrs": {"id": "123"},
  "mode": "void",
  "children": []
}
```

字段定义如下：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `type` | 字符串 | `text` 或 `element` |
| `text` | 字符串 | Text 节点的字符内容 |
| `name` | 字符串 | 元素名称 |
| `attrs` | 字符串到字符串的映射 | 元素属性 |
| `mode` | 字符串 | `void` 或 `block` |
| `children` | 节点数组 | 原子元素为空；容器元素包含子节点 |

解析器必须合并相邻 Text 节点并移除空 Text 节点。属性值必须是 Unicode 标量值序列，不允许未配对的代理码位。属性顺序不属于语义。`void` 与 `block` 有区别，即使 `block` 的子节点数组为空也应保留其模式。

例如：

```cqx
你好 [@123]！
```

解析得到：

```json
[
  {"type":"text","text":"你好 "},
  {"type":"element","name":"at","attrs":{"id":"123"},"mode":"void","children":[]},
  {"type":"text","text":"！"}
]
```

## 7. 规范化序列化

规范化序列化（canonical serialization）负责把合法的规范化 AST 转回唯一的 CQX 文本。

序列化器必须遵守以下规则：

1. 所有元素均写成通用形式 `[:name .../]` 或 `[:name ...]...[/name]`。
2. 属性按名称的 Unicode 码点顺序升序排列。属性名称为 ASCII，因此等价于 ASCII 字典序。
3. 每个属性值均以 JSON 双引号字符串输出；不使用裸值。
4. 字符串使用 JSON 的最短常用控制字符转义：`\b`、`\f`、`\n`、`\r`、`\t`；其余 U+0000–U+001F 控制字符使用小写十六进制 `\u00xx`。双引号和反斜杠分别写作 `\"`、`\\`。其他 Unicode 字符原样输出，不转义 `/`。
5. 正文 Text 中的 `\` 编码为 `\\`，`[` 编码为 `\[`；其他字符原样输出，包括换行。
6. 不插入排版缩进、额外空格或换行；相邻节点直接连接。
7. 保留元素名称的大小写、元素顺序及 `void`/`block` 模式；不执行 Unicode 归一化。

例：

```cqx
你好 [@00123]！[img cat.png]
```

规范化结果：

```cqx
你好 [:at id="00123"/]！[:img src="cat.png"/]
```

合并转发：

```cqx
[forward]
  [msg user=1]你好[/msg]
  [msg id=42/]
[/forward]
```

规范化结果：

```cqx
[:forward][:msg user="1"]你好[/msg][:msg id="42"/][/forward]
```

对通过语义验证的规范化 AST `T`，实现必须满足：

```text
parse(serialize(T)) == T
serialize(parse(serialize(T))) == serialize(T)
```

这里比较的是节点语义，不包括输入时选择的简写、属性排列与排版。`forward` 的间隔空白属于第 5 节规定的可忽略排版内容。

## 8. 严格解析与错误处理

符合规范的严格解析器至少执行以下阶段：

1. 逐字符扫描，识别正文转义、已登记简写及通用标记。
2. 读取标记头部，正确处理引号内部的 `]` 与 JSON 转义。
3. 解析名称和属性，拒绝重复属性及非法属性值。
4. 通过栈或递归方式匹配容器结束标签。
5. 合并相邻文本节点，应用 `forward` 排版空白规则。
6. 检查内置元素的原子/容器模式、必需属性及 `msg` 结构约束。

严格解析器遇到非法 CQX 标签必须报错，并至少提供错误位置。对于通常不构成 CQX 标签的普通方括号文本，解析器应保留为正文。

| 输入 | 处理结果 |
| --- | --- |
| `[note]` | 普通文本 |
| `\[@123]` | 普通文本 `[@123]` |
| `[@123]` | 提及元素 |
| `[img]` | 错误：缺少 `src` |
| `[:x]` | 错误：缺少 `[/x]` |
| `[b]内容[/i]` | 错误：结束标签不匹配 |
| `[/x]` | 错误：多余的结束标签 |
| `[:x a=1 a=2/]` | 错误：重复属性 |
| `[forward]hello[/forward]` | 错误：`forward` 直接包含非空白文本 |
| `[msg id=1]你好[/msg]` | 错误：引用节点必须是原子元素 |
| `[msg user=1/]` | 错误：自定义节点必须是容器元素 |

建议解析器提供最大输入长度、最大嵌套深度与最大节点数限制。实现可以额外提供宽容模式；宽容模式的输出必须与严格模式明确区分。

## 9. 与其他协议的映射

CQX 定义内容模型，不定义消息发送 API。适配器负责名称及参数映射、附件处理、权限检查、平台能力验证和发送失败报告。

以下为建议的 OneBot 11 映射：

| CQX | OneBot 11 消息段或结构 |
| --- | --- |
| `at(id=...)` | `at` 段，`qq=...` |
| `img(src=...)` | `image` 段，`file=...` |
| `reply(id=...)` | `reply` 段，`id=...` |
| `face(id=...)` | `face` 段，`id=...` |
| `forward` | 合并转发发送接口所需节点列表 |
| `msg(id=...)` 原子节点 | 引用节点 `node(id=...)` |
| `msg(user=...,name=...)` 容器节点 | 自定义节点 `node(user_id=...,nickname=...,content=...)` |

这些字段映射由适配器完成，音视频与文件资源还需进行平台特定转换。对不支持的元素，适配器必须报告不支持，或在调用方明确指定降级策略后执行降级。

## 10. 输入安全与实现约束

- 接收普通用户文本时，宿主应默认采用**纯文本模式**。需要构造富消息时，由调用方明确启用 CQX 解析。
- 解析标记不执行网络请求、文件访问、脚本或插件动作。扩展元素的 `action` 等字段只是数据。
- 发送前应按目标适配器校验提及权限、链接与媒体资源策略、元素能力和结构约束。
- 实现应限制输入长度、节点数、深度及属性大小，防止恶意深度嵌套和超大消息消耗资源。
- 未知通用元素必须能够在 AST 与规范化文本之间往返；适配器可以因能力不足拒绝发送。

| 输入 | 规范化结果 |
| --- | --- |
| `你好 [@123]！` | `你好 [:at id="123"/]！` |
| `[@all]` | `[:at type="all"/]` |
| `[img cat.png]` | `[:img src="cat.png"/]` |
| `[reply 42]` | `[:reply id="42"/]` |
| `[file a.pdf name="资料.pdf"]` | `[:file name="资料.pdf" src="a.pdf"/]` |
| `[b]重点[/b]` | `[:b]重点[/b]` |
| `[:vendor.x z=9 a=2/]` | `[:vendor.x a="2" z="9"/]` |
| `[:x/]` | `[:x/]` |
| `[:x][/x]` | `[:x][/x]` |
| `[note]` | `\[note]` |
| `\[@123]` | `\[@123]` |

**多行合并转发：**

```cqx
[forward]
  [msg user=1 name="Alice"]你好[/msg]
  [msg id=42/]
[/forward]
```

规范化结果：

```cqx
[:forward][:msg name="Alice" user="1"]你好[/msg][:msg id="42"/][/forward]
```

## 附录 A：简化文法

以下 EBNF 描述通用标记的结构。简写由封闭的内置简写表补充；纯文本识别按第 3 节的扫描规则执行。

```ebnf
Document       = { Text | Element } ;
Element        = GenericVoid | GenericBlock | BuiltinShorthand ;
GenericVoid    = "[:", Name, Attributes, "/]" ;
GenericBlock   = "[:", Name, Attributes, "]",
                 Document, "[/", Name, "]" ;
Attributes     = { Whitespace, Attribute } ;
Attribute      = Key, "=", (BareValue | JSONString) ;
Name           = Letter, { Letter | Digit | "_" | "." | "-" } ;
Key            = (Letter | "_"), { Letter | Digit | "_" | "." | "-" } ;
Whitespace     = (" " | "\t" | "\r" | "\n"), { " " | "\t" | "\r" | "\n" } ;
```

`BareValue` 为第 2.2 节定义的非空裸值，`JSONString` 为 JSON 双引号字符串。为了可靠实现，解析器应先识别字符串引号，再寻找标签末尾的 `]`；不应使用不考虑字符串与嵌套状态的单条正则表达式解析整份文档。

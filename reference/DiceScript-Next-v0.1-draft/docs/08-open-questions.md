# 08 · 语义未决项（不含实现计划）

这些是仍需语言设计讨论的**具体语义问题**，而非开发步骤。v0.1 其余已写明的规则可以独立讨论；这里列出的地方不应被视作最终确定。

1. **命名与扩展名**：DiceScript Next / `.rdl` 都是本文暂用名，不代表项目正式名称。
2. **基础骰点修饰组合**：先 `min/max` 后 `keep/drop` 的顺序已明确；但是否允许多类筛选组合，以及历史别名需进一步对照 DiceScript 实际语义，当前选择直接拒绝重复筛选。
3. **CoC、Fate、WoD、DX 完整规则参数集**：v0.1 保证有规则字面量入口；各规则参数别名、边缘行为及轨迹元数据需进一步冻结；特别是 Double Cross 对象函数签名。
4. **对象字段的静态形状与动态添加**：当前允许动态增加字段，静态类型分析倾向于警告疑似拼写错误，但这种警告在明确“开放对象”场景下应如何控制尚未定义。
5. **对象与闭包可变性/公式捕获**：Formula 捕获常量或对象快照；对象图共享与可变性对快照的精确定义还需形式化。
6. **展示协议**：Roll 默认插入总值，`detail` 显示过程；未来是否区分 `to_text(style)` 或宿主展示选项留作讨论，不能用隐藏状态改变同一程序的语义。
7. **数值与集合边界**：保留 `Int64` 与有限 `Float64`，字符串下标按 Unicode 标量；如需要 Decimal、超大整数、字素簇，应显式修订，而非悄悄改变实现。
8. **类型标注的使用体验**：当前推断绑定类型；是否允许 `x := null` 后自动拓宽到其他类型有争议，v0.1 暂不允许，推荐 `x: Int? := null` 或 `x: Any := null`。
9. **字面量内的保留方法名冲突**：用户字段遮蔽 `.keys()` 一类内建方法，提供 `Object.keys(o)` 脱困，后续可讨论是否改用纯函数优先。
10. **骰点解析 Unicode 容错**：现有 DiceScript 一定程度容忍全角符号；新语言应在完整词法层对兼容全角标点发出修复建议还是直接自动归一化，尚未确定。当前草案严格解析并给出建议。

**不在讨论范围**：引入类继承体系、模块/包管理器、泛型系统、异步 IO、浏览器 API、插件框架或以新语言替代完整 JavaScript。这些超出“DiceScript 与 JS 中间位”定位。
